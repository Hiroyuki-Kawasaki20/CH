# CHかんばんセット 仕分け・割り振りルール

この文書は、CHかんばんセットで実際に適用される仕分け・工程割り振りロジックを、運用者向けに明文化したものです。
実装基準は `src/services/sorter.py`、`src/services/scheduler.py`、`src/services/process_assigner.py` です。

## 1. 対象と前提

- 対象: 便名・受入・オーダーで絞り込んだ出荷情報
- 1レコードは `PLANKANBANSU` 分だけ展開され、1行=1パレットとして扱う
- 山の高さ上限は 2450mm
- セットボードはメイン・リリーフ・あふれの3レーン表示
- 引取工数の計算式:

```text
引取工数(秒) = Max移動工数 + 187.64 + (パレット数 - 1) * 3.247 + パレット数 * 52
```

### 1.1 便名・受入・オーダーの突合ルール（Issue #110）

画面左ペインの「便名 → 受入 → オーダー」の候補は、出荷情報と出荷場一覧を次の条件で突き合わせて作る。
実装は `src/services/data_loader.py` の `DataManager`。

- 便名: 出荷情報の `納入先` を正規化した値（`TMK`/`九州` → `KVC`、`日野E/H` → `日野EH` 等）が、出荷場一覧の `便名` と一致すること
- 受入: 出荷情報の `UKEIRE` と出荷場一覧の `受入` を**双方**正規化して比較する（数字のみは先頭ゼロを除去。`06` と `6` は同値。`B7` などの英数字混在はそのまま）
- オーダー: 出荷情報の `NONYUHIBIN` が一致すること
- 複数の便を同時に選んだ場合は、**選択ごとに独立したマスクを作って OR で合成**する（条件を先に AND で束ねない）

かつては上記に加えて `SSYUKKA == 仕入先工区`・`納入先コード == 納入先コード`・`SYUKKAKOKU == 納入先工区` を AND する「厳密突合」があった。
しかし実データでは `SSYUKKA` が全行 `02N`、出荷場一覧の `仕入先工区` が `01N`/`11N` のみで積集合が空になり、
突合結果が常に0件（＝GUIで便を選んでもデータが割り振られない「仕分けもれ」）となっていたため撤去した（Issue #110）。

#### 割り振り対象外データの警告

出荷場一覧に `(便名, 受入)` の行が無い組合せは、オーダーは選べても受入が1件も出ないため選択が完成せず、割り振り対象外になる。
これを無言で落とさないよう、実行時に警告ポップアップ（タイトル「未登録アラート」）で件数を表示する。

```text
出荷場一覧に未登録の組合せがあるため、次のデータは割り振り対象外です。
  ・KVC/B3 37行(37パレット)
  ・織機/21 48行(53パレット)
合計 85行 / 90パレット
```

対応は、出荷場一覧に該当の `(便名, 受入)` 行（`納入先コード`・`納入先工区` を含む）を登録すること。
実装箇所:

- `src/services/data_loader.py` — `collect_unreachable_summary()` / `build_unreachable_warning_message()`
- `src/app/gui.py` — `_show_unreachable_pair_warning_popup()`

## 2. 仕分けルール

### 2.1 共通ルール

- 入車時間マスタがある場合、各行に「入車時間」を付与する
- 基本はファーストフィット(上から順に積む)で山を作る
- 入車時間が異なるパレットは同一山にしない(同一サイズ種類内で入車時間ごとに独立積み)

### 2.2 サイズ種類ごとの扱い

- サイズ種類 1:
  - 便ごとにローカル山を作成後、混載を行う
  - 混載は最大3山まで
- サイズ種類 4:
  - 入車時間あり: 入車時間単位で再積み
  - 入車時間なし: 便番号単位で再積み
- その他サイズ:
  - 基本グループ単位で山通番を採番

### 2.3 サイズ種類1の混載条件

- 混載候補は高さ上限 2450mm 以内で選ぶ
- 原則: 同一納入先で便番号が異なる組み合わせは混載禁止
- 例外: 納入先が `KVC` または `元町` で始まり、かつ入車時間が一致する場合は、便番号が異なっても同一山への混載を許可
- 納入先の正規化（例: `TMK` → `KVC`）は山結合判定の前に行う。したがって、統合例外判定は正規化後の納入先で評価される
- 2山混載を確定後、余裕があれば3山目を追加
- 混載キー列(既定: `UKEIRE`)は集計用。混載可否判定自体は「納入先×便番号差異」で判定
- **【特例品番】品番 631426010000（サイズ1）は、サイズ21の山との混載を禁止。他のサイズ1パレットとの混載は許可される**。高さ例外（2165mm 上限）は維持される。

### 2.4 混載後の救済分割(競合解消)

サイズ種類1の混載後、次の条件を満たす山は分割対象:

- その山に含まれる便の最小締切(入車-20分)が
- その山に必要な最大開始下限(前便入車+10分)より早い

このとき、山内で最も締切が厳しい納入先を別山へ分離し、締切違反を回避する。

## 3. 山統合ルール

- サイズ種類1(混載済み)の山通番を先に確定
- その後、サイズ種類4とその他サイズを後続番号で連番採番
- 最終的な山通番は、山構成を変えずに「オーダー番号(NONYUHIBIN末尾2桁)昇順 → 同一オーダー内はサイズ種類順」で再採番する（この採番は、便集荷順・リリーフ挿入を含む工程最適化ロジックとは独立）
- 最終明細は山通番昇順、同一山内は移動工数降順

### 3.1 山内パレット（GroupedData）の番号採番ルール

SPOアップロード用 GroupedData の「番号」列は **移動工数の昇順** で 1, 2, 3 … と採番する。

- 第1キー: 移動工数 昇順（数値比較）
- 第2キー（同値安定化）: SEBANGO 昇順。SEBANGO 列が存在しない場合は 工程内No 昇順。
- 移動工数が NaN のパレットは末尾（番号最大）とする。
- 移動工数列が存在しない山は全行 NaN 扱いとなり、入力順（DataFrame の行順）で採番する。
- SPOアップロード用の「引取開始時間」は、GroupedData 内の候補便のうち最も早い開始候補を採用する。
- 便が 1直・2直にまたがっていても、深夜側の候補を優先して上書きしない。

実装箇所: `src/services/exporter.py` — `build_groupeddata_json_for_mountain()`

> **検証例（06便 NONYUHIBIN=2026070110）**
> | ストア | 移動工数 | 番号 |
> |---|---|---|
> | Q10-B-7  | 72.908（最小） | 1 |
> | Q10-A-11 | 72.911         | 2 |
> | Q10-A-12 | 72.912         | 3 |

## 4. 割り振り(メイン/リリーフ)ルール

### 4.0 割り振りエンジンの採用ルール

- まず新スケジューラ（EDF + 同便クラスター連続 + アイドル部分充填）で割付を作成する
- 次に既存ロジックの結果と比較し、目的関数が同等以上のときのみ新スケジューラ結果を採用する
- 目的関数が劣る場合は既存ロジック結果を採用する（後方互換）
- EDF比較を行うのは、山数が `EDF_COMPARE_MIN_YAMAS`（`src/models/constants.py` = 15）を
  **超える**場合、すなわち16山以上のときのみ。15山以下は貪欲法の結果がそのまま最終結果になる
- したがって 4.4 節2項の前倒し採用ガードのように「貪欲法の内部」で働く制御は、
  16山以上のケースでは最終結果に現れないことがある。
  効果測定は15山以下のデータで行うこと

### 4.1 用語

- メイン工程: 原則1人で処理する主工程
- リリーフ工程: メインで締切に間に合わない山の退避先
- 各直始業時間: 1直=06:25、2直=16:40
- 引取り可能時間: 入車時間マスタの「入車時間」(納入先×便で紐づく時刻)
- 締切: 引取り可能時間 - 20分(= 入車時間 - 10分)
- 開始下限: その山を開始できる最も早い時刻

引取り可能時間の補足:

- 00:00〜1直開始前(06:25前)の時刻は、運用日タイムライン上で +24時間として扱う
  - 例: 00:20 は 24:20 として評価し、23:xx からの連続性を保つ

### 4.2 開始下限の決め方

- マスタに「セットありフラグ」列がない場合(旧マスタ):
  - 従来ルールを適用
- セットありフラグ=true:
  - 目的: 次直の開始時刻からでは間に合わない便を、前直で準備開始するためのフラグ
  - 同レーンの直前便を基準にする
  - 同レーンの直前便は `参照先オーダー = 対象オーダー - レーン数` で計算する
  - レーン数は品目で固定（変動しない）
    - 日野: 2
    - その他: 1
  - 参照先が先頭側に突き抜ける場合は、同レーンの最終便へ循環して参照する
  - 開始下限は「参照先の入車時間 + ARRIVAL_BUFFER_SECS（10分）」
- セットありフラグ=false:
  - 日野(2レーン)は同レーン直前便(N-2)を参照する
  - 参照時刻が 24:xx/25:xx でも前日側をそのまま採用せず、当日基準に戻したうえで下限を適用する
  - 開始下限は必ず「各直開始 + 15分」を max で適用する
    - 1直の1便目: 06:40以降
    - 2直の1便目: 16:55以降
  - 非日野は従来どおり前便入車+10分

補足:

- 引取開始時刻のバッファは 10分(600秒) を用いる
- 本実装では `ARRIVAL_BUFFER_SECS` がこの定数に対応する
- 日野2レーンの参照便計算（`_is_hino_2lane_target` / `_get_lane_count` / `_get_prev_bin_for_vendor`）は `src/services/process_assigner.py` を単一の参照元とし、バッテリー交換ON時（`scheduler._mountain_context`）も同実装を再利用する

従来ルール(前便入車+10分)の詳細:

- 納入先が武部:
  - 同納入先内で1つ前の入車時間グループ +10分
- その他納入先:
  - 原則、前便番号の入車時刻 +10分
- 日野系納入先:
  - 01便の前便を最終便として循環扱い(例: 11 -> 01)
- 前便が引けない場合:
  - 開始制約なし(0秒)

### 4.3 締切の補正(セットあり便)

セットありフラグ=true の便は、通常締切(入車-20分) / 実効締切 = max(入車-20分, 上限)に加えて、
直ごとのメイン工程上限を下限として締切を補正する。

- 1直: 15:20
- 2直: 25:35(翌01:35)

実効締切 = max(入車-10分, 上記上限)


### 4.4 メイン工程への割り振り

1. 未割当山から、締切が最も早い山を主対象として選ぶ
2. 主対象を遅らせない範囲で、先に処理可能な山があれば前倒し採用（割り込み）
   - 前倒しの可否は「主対象の締切を守れるか」だけでは判定しない。
     割り込みによって**主対象より後ろの山が新たに締切を割る**場合は、その前倒しを見送る
   - 判定は必ず**差分基準**で行う（Refs #96 / #124 / #125）
     - before: 「主対象 → 候補 → 残り全山」の順に置いたときに締切を割る山の集合
     - after : 「候補 → 主対象 → 残り全山」の順に置いたときに締切を割る山の集合
     - `after - before` が空でないとき（＝新たに落ちる山が1つでもあるとき）だけ見送る
     - 件数比較（after の件数 > before の件数）にはしない。
       もともと締切を割っている山を理由に前倒しを全面停止させないため
     - 余裕量のしきい値で候補を事前除外することはしない（#124 で不採用）
   - 時刻の見積りは貪欲法内の共通見積り関数を用い、**照合待ち180秒はここでは加算しない**。
     180秒は後段の実割付（開始時間順に付与）でのみ入るため、ここで足すと
     主対象の締切判定より180秒厳しくなり、前倒しが過剰に止まる
   - 締切は運用日タイムライン（00:00〜始業前は +24時間）へ軸合わせしてから比較する
   - 見送った場合は INFO ログを出力する
     `[GUARD] prefetch blocked: primary=<主対象> candidate=<候補> newly_late=[新たに超過する山]`
   - 実装: `src/services/process_assigner.py`
     — `_pick_next_main_mountain()` / `_makes_others_newly_late()`
     （`_can_keep_primary_deadline()` と AND で併用し、既存判定は変更しない）
3. 仮判定(can_main)の段階でも、実際の割付時と同じ照合待ち(inspection_delay=180秒)を 3山目、5山目、7山目... の開始前に加味して順繋時刻を評価する
4. メインに置いたときに終了時刻 <= 締切ならメイン確定
5. 超過する場合はリリーフへ回す

### 4.5 リリーフ工程への割り振り

- 1山目を含む全山:
  - `max(前山終了, 開始下限)` から最速開始で連鎖配置する
  - 開始下限は「前便入車 + 準備時間バッファ(ARRIVAL_BUFFER_SECS=600秒)」を基準とする
- 並び順:
  - 締切が早い順で評価し、先行山の終了時刻を後続山の下限へ伝播させる
- 空き窓限定の最速前詰め（安全側）:
  - リリーフ/あふれにいる山について、メイン工程の既存タイムラインに「完全な空き窓」がある場合のみ、`max(休憩明け, 前段完了, 開始下限)` から最速で前詰め配置を試行する
  - 窓判定と日野2条件は直列化後の最終時刻を基準に評価する。締切再検証は差分基準（前詰め前から超過している山は許容・前詰めにより新たに超過する山が1件でも生じる移動は不採用）。
  - さらに EDF 案が採用された場合は、後処理適用後のスコア (締切超過件数, 全体終了時刻) が EDF 案より劣化するときは後処理を巻き戻す（劣化ガード）

### 4.6 休憩・照合ルール

- 開始時刻が休憩中、または作業が休憩をまたぐ場合は休憩終了+1分へ繰り下げ
- 短休憩は純休憩10分＋仕分け猶予20分＝引取不可30分（1直 08:30-09:00, 12:55-13:25 / 2直 18:45-19:15, 23:10-23:40）。
- 食事休憩は 10:40-11:25, 20:55-21:40 の45分。引取再開は休憩明け＋1分。
- 照合180秒は工程ごとに独立して付与
- 3山目、5山目、7山目... の開始前に180秒を加算
- 2026-08-25 現場確認・河崎裁定

休憩時間:

- 1直: 08:30-09:00, 10:40-11:25, 12:55-13:25
- 2直: 18:45-19:15, 20:55-21:40, 23:10-23:40

### 4.7 あふれ工程

- メイン工程・リリーフ工程のいずれでも締切に収まらない山は、あふれとして扱う
- あふれはセットボード上の警告・手動確認用のレーンに表示する
- 出力上は工程区分として残し、後工程で再調整できるようにする
- ただし、山を「納入先×便」の作業単位に仮分割すればリリーフで完了可能な場合は、あふれ化せず救済する

### 4.8 直選択と連続実行時の引継ぎ

#### 前回仕分け終了時刻の履歴管理（修正④追加）

- **履歴構造**: 直ごとの工程別終了時刻を最大 2 件（最新 / 1 つ前）保持する
  - 最新: 直前の実行結果
  - 1 つ前: その前の実行結果
  
- **ドロップダウン選択**: UI で「最新 / 1 つ前」を選択可能
  - 初期値は「最新」（現在の実行結果）
  - 1 つ前の実行を再現する場合は「1 つ前」を選択してから実行
  
- **FIFO 更新ルール（A案採用）**: 
  - 実行成功のたびに新しい終了時刻を「最新」として履歴へ push する
  - 元の最新は「1 つ前」に押し出される
  - 最大 2 件を超える場合、最も古いデータは自動的に破棄される
  
- **クリア機能**: 
  - 「引継クリア」ボタンは維持
  - 用途: システムを開いたまま履歴を手動でリセット（限定用）
  - 例: 異なる納入先データセットに切り替える場合など
  
- **永続性**: 
  - 履歴はアプリ内メモリ変数（`lane_end_times_history`）に保持
  - システムを完全に終了すれば自動リセット
  - 再起動時には履歴が消える（保存されない）

#### 直の自動判定（この変更による影響なし）

- 1直 / 2直の基準時刻は変わらず **固定値** で判定される
  - 1直: 06:25
  - 2直: 16:40
- 基準時刻は `process_assigner.py` で入車時刻から自動判定
- 本履歴機能の追加による影響を受けない

#### 引継ぎの適用ルール（従来どおり）

- 実行時に対象の直（1直 / 2直）を選択する
- 引継ぎ時刻は「前回実行と同一直」の場合のみ適用する
  - 同一直: ドロップダウンで選択した時刻（最新または 1 つ前）を次回の開始下限として利用
  - 直切替: 引継ぎを使わず、当該直の基準時刻で初回扱いで再計算
- 手動で引継ぎを無効化したい場合は「引継クリア」を使用する
- アプリ再起動後は引継ぎ情報は保持されない

#### ドロップダウン表示の時刻可視化（修正⑤追加）

- **表示形式**: ドロップダウンの選択肢に工程別の終了時刻を表示
  - 空履歴時: `最新 (未計算)`、`1つ前 (未計算)`
  - データ有時: `最新 (メイン HH:MM / リリーフ HH:MM)`、`1つ前 (メイン HH:MM / リリーフ HH:MM)`
  
- **時刻単位**: HH:MM 形式（時:分）で表示
  - 入力値が秒単位で蓄積されるため、秒単位は非表示（分までの表示）
  - 24時間超過ケース（日をまたいだ作業）: `25:00`、`26:00` のように表示
    - 例: 86400秒 = 24:00、90000秒 = 25:00
    - この表示により、複数直にまたがる長時間作業を視覚的に判別可能

- **意図**: 
  - ドロップダウンを見ただけで前回・前々回の工程別終了時刻がわかる
  - 連続実行時に「現在の履歴がどの直か」を即座に判定可能
  - 実運用で「直が切り替わるなら引継ぎ無効化」という判断を、ユーザが時刻表示で確認できる

- **技術仕様**:
  - 履歴の最大2件分について、毎回「実行完了時」にドロップダウン値を動的に再生成
  - 内部データ（`lane_end_times_history`）は秒単位のまま保持
  - UI表示時のみ、秒→HH:MM への変換を実施（`src/utils/time_formatter.py::seconds_to_hhMM()`）
  - ドロップダウン選択値は「最新 (HH:MM/HH:MM)」のような長形式で表示されるため、
    内部的には正規化処理（`normalize_choice_label()`）で「最新」「1つ前」に変換してから
    履歴選択ロジック（`select_lane_end_times()`）に渡される

## 5. 後処理(時刻の再調整)

### 5.1 メイン工程のT0シフト

- 開始下限で固定されていないメイン山のみ対象
- 全山が締切を満たす範囲で、全体を同一量(T0)だけ後ろへシフト
- 目的: 実運用に近い時刻帯へ寄せる

### 5.2 安全弁

- メイン工程に締切超過が残る場合:
  - まずメイン内を締切優先順で再スケジュール
  - それでも遅れる山はリリーフへ再振り分け

### 5.3 リリーフ最小化

- 再スケジュール後、締切を守ったままメインへ戻せる山を再昇格
- 最終的に「締切違反最小 + リリーフ最小」を目標に収束させる

### 7.2 修正④ 履歴機能の実装（2026-07-15）

**背景:**
- 連続実行シナリオで、実行失敗後に「前回と同じ設定で再実行」するケースが多発
- 直ごとの終了時刻を記録して再利用し、同一条件の再現実行を効率化

**実装方針（TDD fail-first）:**
- テスト駆動開発で fail-first アプローチを採用
- 14個のテストケースで全シナリオを先行定義
  - `push_lane_end_times()`: 履歴への push 操作
  - `select_lane_end_times()`: 履歴から選択値に基づく取得
  - 防御的コピー、FIFO、空履歴ハンドリング
- テスト駆動で純粋関数群を実装（副作用なし）

**実装ファイル:**
- `src/services/lane_end_times_history.py` — pure functions
  - `push_lane_end_times(history, new_times)`: 最新を先頭に insert、最大 2 件 FIFO
  - `select_lane_end_times(history, choice)`: 履歴から「最新」/"1つ前" を取得、unknown は「最新」にフォールバック
- `src/app/gui.py` — UI 統合
  - `__init__`: `lane_end_times_history=[]`, `selected_history_choice=tk.StringVar("最新")`
  - `build_ui()`: Combobox(["最新", "1つ前"]) で 1直/2直 ラジオボタンを置換
  - `run()`: 先頭で `select_lane_end_times()` で前回時刻取得、成功時に `push_lane_end_times()` で新結果記録
  - `clear_lane_time_carryover()`: `self.lane_end_times_history = []` でリセット
  - `recompute_process_assignment()`: 工程割当時に `select_lane_end_times()` で時刻を取得、作業用変数と確定履歴を分離

**テスト状況:**
- テストファイル: `tests/unit/test_lane_end_times_history.py` (14個テスト)
- 全テスト成功: ✅ 14/14 PASSED
- 既存テストへの回帰: ✅ 83/84 成功（1件は既知の不安定テスト）

**重要な設計原則:**
- **確定タイミング**: 実行成功時のみ履歴に push（エラー時は記録しない）
- **防御的コピー**: 履歴内の辞書は常に copy() で防御的コピー（外部からの変更防止）
- **分離原則**: 作業用変数（`working_lane_end_times`）と確定履歴（`lane_end_times_history`）を厳密に分離
- **FIFO と最大値**: 直ごとに最大 2 件を保持、最古は自動破棄
